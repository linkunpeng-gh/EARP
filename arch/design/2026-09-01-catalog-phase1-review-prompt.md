# EARP Catalog Phase 1 设计评审

## 一、评审背景

EARP 产品的 Catalog（语义目录）模块完成了 Phase 1 设计，包括技术架构设计和产品页面设计。现组织相关人员进行评审，确认设计方向、识别风险、提出改进建议。

**评审对象（两份文档）：**

1. **技术设计**：`arch/design/2026-09-01-n01a-catalog-phase1-design-jqmk.md`
   - Catalog manifest 设计（schema、ID、hash、存储）
   - Resolver contract vectors（正向/负向/批量/一致性/生命周期）
   - 三层 Pack 与 pack lock
   - 运行门禁证据（admission、fail-closed、CI、演练、RBAC）
   - 产品化能力（出厂最小集、平台配置、pack 导出、权限审批）
   - 源系统与同步机制（单一数据源、pull+webhook）
   - 13 个决策点（A-M）的结论

2. **产品页面设计**：`arch/design/2026-09-01-catalog-product-pages-design.md`
   - 5 个新建页面的详细设计（字段、按钮、操作流、权限）
   - catalog-admin.html（治理中心，5 Tab）
   - profiles.html（项目配置）
   - metrics.html（指标管理）
   - catalog-basics.html（基础配置，4 Tab）
   - binding-templates.html（绑定模板）

---

## 二、评审目标

1. **确认设计方向**：产品定位、架构选型、核心机制是否合理
2. **识别风险和缺口**：技术可行性、安全合规、运维成本、用户体验
3. **提出改进建议**：可操作的优化点，而非泛泛而谈
4. **达成共识**：评审通过后，设计作为 Phase 1 开发的依据

---

## 三、评审人员与关注点

| 角色 | 评审重点 |
|---|---|
| **产品/业务** | 产品定位是否清晰、页面流程是否符合用户习惯、功能是否覆盖业务需求、优先级是否合理 |
| **架构/技术** | 架构选型是否合理、性能和可扩展性、与现有系统的集成、技术债和风险 |
| **数据域** | 指标/实体/关系的语义定义是否准确、源系统同步机制是否可行、canonical input 和 hash 计算是否合理 |
| **安全/合规** | RBAC 权限模型、审批流 separation-of-duties、fail-closed 机制、审计日志、数据隔离 |
| **运维** | 部署和运维成本、故障恢复、灰度和回滚、监控告警 |

---

## 四、评审要求

### 4.1 会前准备

- **必须提前阅读两份文档**，评审会上不逐页念文档，直接讨论问题
- 每人至少准备 **3 个具体问题或建议**，写在评审文档的评论区或单独整理
- 问题要具体到**章节/页码/字段**，避免"整体感觉不太对"这类模糊反馈
- 如果对某个决策点有不同意见，先看 §7 决策点汇总中的结论和理由，再提出替代方案

### 4.2 评审维度

请按以下维度逐项检查：

**1. 产品定位与范围**
- Catalog 定位为"语义聚合与引用治理层"是否清晰？
- "单一数据源"原则（语义编辑在源系统，Catalog 只注册引用）是否合理？
- 出厂最小集（10 项基础配置）是否够用？
- 5 个新建页面的划分是否合理？有没有遗漏或冗余？

**2. 架构与技术**
- 双层存储（git 治理资产 + 数据库运行时数据）是否合理？
- Resolver 通过 API 查询数据库，性能和可靠性是否满足要求？
- manifest hash 计算和 content_hash 校验机制是否可实施？
- 源系统同步（pull 定时 + webhook）是否可行？有没有更好的方案？
- 三层 pack（平台/行业/企业）的冲突覆盖规则是否清晰？

**3. 安全与治理**
- RBAC 权限点（read/request/approve/manifest.publish）是否够用？
- 角色可配置（不硬编码 6 个角色）是否会导致治理失控？
- 审批流 separation-of-duties 是否可执行？
- fail-closed 机制（未注册/已撤销/hash 不匹配→拒绝）是否过于严格？
- LKG 策略（继续+告警）的告警时限和恢复条件是否需要明确？

**4. 可实施性**
- Phase 1 范围（5 个页面 + Resolver API + 同步机制 + contract vectors）是否过大？
- 哪些可以推迟到 Phase 2？
- 有没有依赖外部系统（Ontology metric projection）尚未就绪的风险？
- 数据库表设计是否需要补充？

**5. 用户体验**
- 页面操作流是否顺畅？有没有过多的弹窗和确认？
- 引用注册的三步流程（选源系统→选对象→选版本）是否易用？
- pack 发布新版本的不可变原则会不会让用户觉得繁琐？
- 版本升级和回滚的操作是否清晰？

### 4.3 评审结论分类

每个问题按以下分类标注：

| 级别 | 定义 | 处理方式 |
|---|---|---|
| **P0 阻塞** | 设计有根本性问题，不解决不能开工 | 必须修改后复审 |
| **P1 重要** | 设计有明显缺陷或风险，建议修改 | 修改后可开工，修改结果同步评审人 |
| **P2 建议** | 优化建议，不影响核心设计 | 记录 backlog，择机改进 |
| **已确认** | 无异议，通过 | — |

## 五、评审流程

### 5.1 会前（评审前 1 天）

1. 评审发起人发送两份文档 + 本评审 prompt
2. 评审人阅读文档，在文档中添加评论（建议按章节标注）
3. 评审发起人汇总问题清单，提前发给所有人

### 5.2 会中（建议 90 分钟）

| 时间 | 环节 | 内容 |
|---|---|---|
| 0-10 min | 设计概述 | 设计人用 10 分钟讲清核心设计（不逐页念） |
| 10-40 min | 产品与架构评审 | 讨论产品定位、页面设计、架构选型 |
| 40-65 min | 技术与安全评审 | 讨论 Resolver、hash、同步、权限、门禁 |
| 65-80 min | 风险与优先级 | 识别 P0/P1 问题，确认 Phase 1 范围 |
| 80-90 min | 结论与行动项 | 确认评审结论，分配修改任务和截止时间 |

### 5.3 会后（3 个工作日内）

1. 设计人根据评审意见修改文档
2. P0 问题修改后需复审（可线上确认）
3. P1 问题修改结果同步评审人
4. 最终版本提交 git，作为 Phase 1 开发基线

## 六、评审检查清单

评审人可按此清单快速自查：

### 产品
- [ ] Catalog 的产品定位一句话能说清吗？
- [ ] 5 个页面的功能有没有重叠或遗漏？
- [ ] 用户从"新建项目配置"到"manifest 生效"的全链路是否顺畅？
- [ ] pack 导出/导入作为经验资产沉淀，设计是否够用？

### 架构
- [ ] 双层存储（git + 数据库）的边界是否清晰？
- [ ] Resolver API 的性能目标（< 10ms 缓存命中）是否合理？
- [ ] 源系统同步失败时的降级策略是否明确？
- [ ] manifest 版本不可变 + 回滚产生新 revision，是否可操作？

### 安全
- [ ] 权限点是否覆盖所有操作？有没有越权漏洞？
- [ ] 审批流能不能绕过？
- [ ] fail-closed 会不会导致系统完全不可用？有没有应急方案？
- [ ] 审计日志记录的字段是否满足合规要求？

### 实施
- [ ] Phase 1 范围是否可在预期时间内完成？
- [ ] 有没有未识别的外部依赖？
- [ ] 数据库表设计是否需要在开发前补充？
- [ ] contract vectors（测试向量）的数量和覆盖度是否足够？

## 八、注意事项

1. **对事不对人**：评审的是设计，不是设计者。鼓励提出不同意见，但要给出理由和替代方案。
2. **聚焦 Phase 1**：不要把 Phase 2/3 的需求混进来，超出范围的建议记入 backlog。
3. **可操作性**：每个问题都要能转化为具体的修改动作，避免空泛的"再想想"。
4. **记录决策**：评审中达成的新共识要记录下来，更新到文档的决策点中。
