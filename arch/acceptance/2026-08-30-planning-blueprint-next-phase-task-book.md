## N01——因果建模管理能力

### 目标

让有权限的业务建模人员通过产品界面创建、修改、校验、审核和发布因果模型；发布后的模型形成不可变 Snapshot，可被既有 Blueprint 编译、诊断和审计链路消费。

### 工作内容

**N01A：建模管理 API 与版本生命周期**

- 因果模型、模型版本、节点、边、证据需求、规则和适用范围的 CRUD。
- 明确状态机：`draft → in_review → published → superseded/archived`；已发布版本不可修改。
- 草稿校验：节点/边引用、方向/强度/置信度、DAG 环、入口节点、目标、证据需求、ABox binding、Ontology/Capability Contract 引用。
- 发布：生成 canonical content hash 和 immutable Snapshot，记录校验报告、审核人和发布时间。
- 以已发布 Snapshot 调用现有 compiler；不得让诊断读取草稿或 live 模型。
- 角色与租户隔离：至少区分建模、审核/发布、只读三类权限。

**N01B：可视化因果建模界面**

- 模型列表、版本列表、草稿/审核/已发布状态。
- 图画布：新增节点、连线、删除、方向、强度和置信度编辑。
- 节点侧栏：业务语义、指标/单位、证据需求、目标实体绑定、规则和适用范围。
- 证据需求的可执行字段（Ontology entity/relation、指标、单位、聚合、binding 模板、Capability Contract）必须从受控目录选择；业务说明、假设和备注允许自由填写。
- 目录中没有所需对象时，建模者发起目录扩展申请；数据/平台管理员审核后才成为可引用目录项。首版不允许在建模界面填写 SQL、接口地址、Provider 参数或任意实体/能力标识。
- 校验面板：按“可阻断发布 / 警告”显示，能定位到节点、边或证据需求。
- 发布确认页：明确显示将锁定的模型版本、hash、校验结果和影响范围。

### 验收标准

- 建模人员可在界面完成“3 号矿产量下降”模型，内容与 Case A Fixture 的业务语义等价。
- 保存草稿后可继续编辑；已发布版本不能直接改写，只能复制为新草稿版本。
- 环、悬空引用、缺失 required evidence、无效 ABox binding、未解析的 Capability Contract 均阻断发布。
- 发布生成的 Snapshot 可被现有 compiler 使用；一次诊断固定使用发布时的版本和 hash。
- 两个租户不能读写对方模型；无发布权限的用户不能发布。
- 通过 API、组件/界面和端到端验收测试；人工测试在 N01B 完成后介入。

### 范围边界

- 不在本任务中接真实企业数据 Provider（N03）。
- 不做自动因果发现、LLM 自动建模或多模型融合。
- 不改变 Case A 已冻结的 Snapshot / Trace 语义。

## N02——诊断工作台

### 目标

让业务使用者能发起一次诊断、理解执行状态和结果，并查看可追溯历史。

### 工作内容

- 诊断发起页：问题/对象/时间窗口输入，显示将使用的已发布模型版本。
- 运行视图：计划、采集状态、业务数据不可用与基础设施故障的明确区分。
- 结果视图：原因排序、置信度、证据链、完整性状态和限制说明。
- 历史与 Trace 视图：查看输入、Snapshot、Observation、结果及 audit-only replay。

### 验收标准

- 非技术用户可从界面发起 Case A 诊断并看到 Golden Top 1 与证据链。
- DATA_UNAVAILABLE、PARTIAL、FAILED 与 BLOCKED 在界面上不可混淆。
- 历史结果可定位到唯一模型 Snapshot、Blueprint、Context 和 Trace。

### 范围边界

- 不提供模型编辑能力（N01）。
- 不自动执行纠正措施或生成决策建议（N04）。

## N03——一个真实只读数据 Provider

### 目标

在不破坏 mock Fixture 验收可重复性的前提下，接入一个受控的真实只读数据源。

### 工作内容

- 选定一项低风险只读 Provider，并明确数据责任人、认证方式、字段字典、刷新频率与测试环境。
- 实现 Adapter：身份认证、时间窗口查询、字段映射、数据质量判断和错误分类。
- 把真实返回标准化为既有 Observation 合同；保留 mock Provider 供 CI 和离线验收。
- 监控、脱敏、访问审计和失败降级。

### 验收标准

- 在批准的测试环境中完成一次真实只读查询和一次 Case A 诊断。
- 业务无数据与认证/网络/Provider 故障仍分别映射为现有业务终态与基础设施失败。
- 不向日志或 Trace 写入敏感原始凭据；mock E2E 不依赖真实环境。

### 前置条件

- 业务方确认数据源、字段含义、访问账号、测试数据和安全边界。

## N04——Case B 决策推荐验收设计

### 目标

从“解释为什么发生”扩展到“解释可采取哪些措施及其约束”，先形成可评审、可验收的设计，不直接自动执行动作。

### 工作内容

- 选定单一决策场景，定义业务目标、候选措施、约束、风险、预期收益和人工审批点。
- 定义决策模型、输入输出合同、Fixture、Golden recommendation 和拒绝/降级路径。
- 定义与 Case A 诊断结果的衔接、Trace 边界及人工验证脚本。

### 验收标准

- 形成评审通过的 Case B PRD、因果/决策/业务模型、Fixture 和 E2E 验收规格。
- 推荐结果可说明“基于哪些诊断证据、受哪些约束、为什么不自动执行”。

### 范围边界

- 本任务只做设计与验收规格；实际推荐引擎、动作执行和自动化闭环另立实施任务。

## N01 讨论起点

N01 先确认以下四项设计决策，再进入 API/界面原型：

1. **建模粒度：** 一个模型版本是否只对应一个因果图和一个业务目标？建议是，避免首版把不同诊断目标混在一个发布单元。
2. **发布治理：** 是否采用“建模者提交、审核者发布”的双人流程？建议生产环境采用；开发/演示租户可配置为同一角色。
3. **证据需求配置：** **已确认。** 可执行字段必须复用受控 Ontology、指标目录、binding 模板与 logical Capability Contract；业务解释字段可自由填写。缺少目录项时走申请与审核流程，首版不允许自由文本 SQL、接口地址或 Provider 参数。
4. **图编辑体验：** 首版是否只支持 DAG、手工连线和表单属性编辑？建议是；自动布局可有，自动发现/LLM 生成留到后续。
