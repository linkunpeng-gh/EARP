## 0. 30 秒看懂 Chatflow

Chatflow 是**独立于 Chat 的一种应用**（工作台抽屉里两个并列标签）：

| | Chat 聊天助手 | **Chatflow 流程编排（本文主角）** |
|---|---|---|
| 怎么干活 | 机器全自动（理解→检索→回答） | 你在**画布**上拖一张图规定步骤 |
| 入口 | 工作台 → **chat** | 工作台 → **chatflow**（独立标签） |
| 适合 | 通用知识问答 | **流程固定的场景**（如"先查设备状态→坏了就建工单→人工确认"） |

一张流程图画布长这样：

```
[开始] → [QU 理解] → [能力调用:查状态] → [工具:取中台数]
     → [条件: 状态==故障?]
          ├─ ✓是 → [人工确认] → [LLM 生成工单] → [结束]
          └─ ✗否 → [LLM 生成"正常"答复] → [结束]
```

**骨架（先干什么后干什么）是你拖的；节点内部怎么理解、怎么查，是机器自动的。**

三个关键概念先记住（后面都会用到）：

- **节点之间靠"变量"传值**：上一个节点的输出，用 `{{#节点id.字段#}}` 拿给下一个节点用（见 §4）
- **人工确认会"挂起"**：流程走到人工确认节点会停下来等你回复，你回一句它继续跑（见 §6 第 6 条 / §7.5 第 5 步）
- **多轮对话里"它/这台设备"能指代上文**：你说过 CNC-01，下一句说"它坏了"，流程知道指的是 CNC-01（见 §6.6）

## 2. 画布编排页长什么样（Dify 式三栏）

```
┌─────────┬──────────────────────────┬───────────────┐
│ 节点面板  │         画布             │  属性面板       │
│ ▸ 开始   │  [开始] → [LLM]          │  选中节点配置   │
│ ▸ LLM   │     ↓                    │  提示词: …     │
│ ▸ 知识检索│  [条件] → [人工确认]      │  (字段随节点变)  │
│ ▸ QU    │   (拖节点+连线+平移+缩放)  │               │
│ ▸ 能力…  └──────────────────────────┴───────────────┘
└─────────  顶部栏：流程名 + ▶运行 + 保存 + 发布
```

- **左·节点面板**：11 种积木（见 §3 节点字典），**拖到画布**（或双击快速添加）
- **中·画布**：拖节点、连线（右圆点 → 左圆点）、平移（拖空白）、缩放
- **右·属性面板**：点选中节点，编辑它的参数（字段随节点类型变化）
- **顶部**：▶ 运行（测试）、保存、发布

## 3. 节点字典（这 11 种"积木"）

| 节点 | 干什么 | 属性面板里配（必填） | 会输出什么（下游可引用） |
|:---|:---|:---|:---|
| **开始 / 结束** | 流程起点 / 终点 | 无（一张图各一个） | — |
| **LLM** | 生成文字/回答 | 提示词 `prompt`（可选：系统提示词、选模型） | `text`（生成的话） |
| **知识检索** | 知识库检索 | 检索词、TopK | `chunks`（命中片段，含 metadata）、`citations`（引用） |
| **QU 理解** | **自动理解问题**（识别实体/意图）再查 | 理解问题（默认用用户问题）；「启用 LLM 升级」勾选（取消=纯规则更快） | `entities`（提到的实体）、`citations`（引文）、`chunks`、`selection`（选了哪个策略） |
| **能力调用** | 调系统能力（带权限+审计） | 能力 ID（来自能力中心） | 能力执行结果（如查状态→`rows` 列表） |
| **工具取数** | 经中台连接取数 | 连接 ID（来自中台对接） | `rows`（数据行）、`count`（行数） |
| **对话历史** | 取最近对话 | 轮数 | `messages`（历史消息） |
| **条件分支** | 条件分流（俩出路） | 左值(前节点输出)、操作符、右值 | 走 ✓是 或 ✗否（不产出数据） |
| **人工确认** | **停下来等人工** | 确认问题 | `reply`（你回的答复） |
| **注释** | 画布上写说明文字，**不执行** | 注释内容（可空） | — |

> **条件节点**有 2 个输出口：第 1 个输出 = ✓是，第 2 个输出 = ✗否（连线时注意）。
> **mcp 节点暂未支持**——别放。
> 「会输出什么」的具体字段和写法见 §4.5。

## 4. 变量引用（让节点之间传值）

在属性面板的文本框中可直接写：

| 写法 | 含义 |
|:---|:---|
| `{{query}}` | 用户这次的问题 |
| `{{#节点id.output.字段#}}` | 某个前序节点的输出（如 `{{#q1.output.citations#}}` 取 QU 的引文） |
| `{{#节点id.output.reply#}}` | 人工确认节点的答复 |
| `{{#节点id.输出列表.下标.字段#}}` | **列表首元素引用**（F6）：`{{#qu1.entities.0.mention#}}` 取 QU 理解的第一个实体（如 CNC-01）；`{{#k1.chunks.0.metadata.customer#}}` 取检索结果第一条的元数据 |

例：LLM 节点提示词 `用户答复：{{#h1.output.reply#}}。请生成工单摘要。`
→ 运行时自动替换成"用户答复：同意派单。请生成工单摘要。"

例：能力节点输入 `{{#qu1.entities.0.mention#}}` → QU 理解出实体（CNC-01 数控机床）后，能力调用收到该设备引用。

## 4.5 每个节点能输出什么（传参速查）

> 这是把流程"串起来"最常用的一张表——上一个节点的输出怎么拿给下一个节点用。
> 写法统一是 `{{#节点id.字段#}}`；**拿列表的第一条**就在字段名后加 `.0.` 再写子字段（F6 起支持）。

| 节点 | 输出字段 | 典型写法 | 用途示例 |
|:---|:---|:---|:---|
| **QU 理解** | `entities`（实体列表） | `{{#qu1.entities.0.mention#}}` | 把 AI 识别出的设备名（如 CNC-01）传给查状态能力 |
| QU 理解 | `citations` / `chunks` | `{{#qu1.citations#}}` | 让 LLM 按检索结果回答 |
| **知识检索** | `chunks`（含 metadata） | `{{#k1.chunks.0.metadata.customer#}}` | 取检索命中的客户名；`{{#k1.chunks.0.metadata.vip#}}` 判断是否 VIP |
| **能力调用** | 执行结果 | `{{#c1.output.rows.0.status#}}` | 取设备状态（查状态能力返回的 rows 第一行） |
| **工具取数** | `rows` / `count` | `{{#t1.output.count#}}` | 取数据行数 |
| **人工确认** | `reply` | `{{#h1.output.reply#}}` | 把用户答复写进后续通知/工单 |
| **LLM** | `text` | `{{#l1.output.text#}}` | 把前一个 LLM 的结果再加工 |
| **对话历史** | `messages` | `{{#m1.output.messages#}}` | 让 LLM 参考历史对话 |

**条件分支的左值**也按同一套路径写：`c1.output.rows.0.status`（节点 id + output + 路径）。
判断"列表第一条"：路径中间加数字下标即可，如 `rows.0.status` / `chunks.0.metadata.vip`。

## 5. 四步搭好一个流程

1. **点「示例」**按钮载入模板打底（全节点示例），删掉/改不需要的
2. **从左边拖节点、连边**，点节点在右边配参数（capability_id / connector_id / 提示词…）
3. **点「保存」**——图不合法会提示（缺开始/结束、有环、条件分支只连一条…）→ 修正再存
4. **点「发布」**——上线前发布评审会再校验一次图；已发布应用再改会**回到草稿**，需重新发布才生效

> 保存后点「▶ 运行」就能测（见 §6）；保存会把**节点位置**也记住——重开画布不会乱跑，拖好位后随时再保存。

## 6. 调试（跑你的流程）

1. 点「**▶ 运行**」→ 输入一句测试问题 → **画布底部出现结果条**：用户问题 + 答案 + 状态统计（N 执行 / N 跳过 / N 失败）
2. **画布节点就地着色**：执行过的节点**左侧绿条 + ✅**（节点上直接显示输出摘要）；未命中分支**灰色 ⏭**；失败**红色 ❌**；人工确认等待**粉色 ⏸**——一眼看出哪条路走了
3. **点任意节点** → 右侧属性面板下方「运行详情」：该节点的**状态 / 耗时 / 实际输入 / 输出 / 错误**
4. **结果条可调**：拖结果条上边缘调高度（会记住）；可展开「全部节点轨迹」看每步输入输出与耗时
5. **遇条件分支** → 按命中分支走，另一支不执行（画布上直接看到 ✓是 / ✗否）
6. **遇人工确认** → 结果条内联「⏸ 等待确认」→ 输答复提交 → 流程继续跑完
7. **出错** → 节点染红 + 红色提示（权限 403 / 图画错 / 执行失败），点节点看错误详情

**失败是什么样的（实测语义）**：某个节点失败 → 流程状态为 **failed**（不返回 500），
**后面的节点不执行**、**已做的操作不撤销但也不会再多做**（如已开的单不会重复开）。
具体哪一步挂的、为什么挂，看结果条「全部节点轨迹」里那个红 ❌ 节点的错误信息。

> 同一会话可多个人工确认点，逐个等待、逐个答复。刷新后画布布局保持（位置已保存）。

## 6.5 节点配置细节（LLM 模型 / QU 调节）

**LLM 节点**：属性面板＝① 提示词（User，本轮任务，支持变量引用）② 系统提示词（角色/规则，可选，每轮稳定生效）③ 模型（下拉：`默认（应用配置）` 或从**模型配置中心**选一个模型——该节点就用它执行）。只填提示词也能跑，但复杂流程建议把固定规矩写进系统提示词。

**QU 节点**：「启用 LLM 升级」勾选（默认）＝低置信时用 LLM 补全语义理解（更准，略慢）；取消勾选＝**纯规则理解（秒回）**——速度敏感或规则已够用时取消。

**QU 输出什么**：QU 不只是"查一下"——它会输出**识别到的实体**（`entities`，如 CNC-01）、**选了哪个查询策略**（`selection`）、**检索引文**（`citations`/`chunks`）。下游节点最常用的是：
- 条件分支判断实体/意图：左值写 `qu1.output.entities`（或 `qu1.output.selection.plan_name`）
- 能力节点要设备名：`{{#qu1.entities.0.mention#}}`
- LLM 按检索回答：`{{#qu1.citations#}}`

**实测耗时差异**（qwen2.5:1.5b 本地）：纯规则 QU 约 **60ms**；开 LLM 升级后冷启动第一次约 **8 秒**（模型加载），模型热了之后约 **70ms**。所以"慢"基本是模型冷启动或 LLM 生成，不是流程本身。

**QU 升级模板**（管理员配置）：模型配置中心 → 系统模型设置 → 「QU 升级模板」——留空＝内置默认；点「**载入默认**」以默认内容为底稿修改。占位符：`{query}` 用户问题、`{missing}` 待补字段、`{relation_candidates}` 关系候选、`{context}` 上下文。保存内容=默认等价于留空。

> 模型配置中心里改**系统默认 LLM**，会影响所有未单独指定模型的应用/节点。

## 6.6 两轮对话：指代消解（"它"指上文哪个设备）

用户连着问两句，第二句用"它/这台设备"指代——流程会自动把**上一句提到的实体**接上（F6 已验证）：

```
用户：CNC-01 温度异常，请帮我处理
用户：它刚才还报警了          ← 「它」= CNC-01（QU 节点自动识别，无需配置）
```

- **怎么生效**：不需要配任何东西。QU 节点理解第二句时，会从**同一个会话**的上一句用户消息里
  取实体作为上下文（规则层指代映射，非 LLM 盲猜）
- **限制**：指代解析依赖上一句提到实体。如果上一条是人工确认的"确认"之类没实体的消息，
  指代源为空——这时第二句最好把设备名写全
- **验证**：调试时点 QU 节点看运行详情里的 `entities`——第二句应能看到 `CNC-01 数控机床`

## 7. 三个常用场景示例

### 场景 A：知识问答（最简单）
```
开始 → 知识检索 → LLM 生成回答 → 结束
```

### 场景 B：设备维修单（确定性流程 + 人工把关）
```
开始 → QU 理解（"CNC-01 温度异常"）→ 能力调用:查状态
     → 条件: 状态==故障?
          ├─ ✓是 → 能力:建工单 → 人工确认（确认派单）
          │       → 能力:通知负责人 → 结束
          └─ ✗否 → LLM 生成"设备正常"答复 → 结束
```

### 场景 C：客户投诉分流（规则分支）
```
开始 → 知识检索:查历史投诉 → 条件: 是否 VIP?
      ├─ ✓是 → 专人话术 → 结束
      └─ ✗否 → 标准话术 → 结束
```

## 7.5 照着搭：设备维修单（场景 B）完整实操

> 场景 B 的成品已在 dev 环境跑通（评估脚本 `scripts/verify_f6.py`，78 项断言全绿）。
> 下面是**从零搭一遍**的完整步骤——照着做能复现「查状态→故障→开单→人工确认→通知」全流程。

### 第 1 步：起一个“外部系统”（演示用 mock，生产接真实系统）

```bash
python scripts/f6_mock_server.py        # 端口 8001
curl http://127.0.0.1:8001/health       # {"status":"ok"}
curl http://127.0.0.1:8001/equipment/status?equipment_id=CNC-01
# → {"data": [{"equipment_id": "CNC-01", "status": "faulty", "temperature": 78.5}]}
```

mock 的**控制端点**（评估/演示时切状态用，不进流程）：

| 端点 | 作用 |
|:---|:---|
| `POST /_control/equipment` body `{"equipment_id":"CNC-01","status":"ok","temperature":42}` | 把设备改成正常/故障，看另一条分支 |
| `POST /_control/reset` | 重置全部设备状态 + 清空调用记录（重跑前调用，保证断言干净） |
| `GET /_state` | 看当前设备状态、已开单/已通知/已归档记录（验证副作用） |

### 第 2 步：注册 3 条连接（中台对接 → 连接管理）

| connector_id | 类型 | config |
|:---|:---|:---|
| `cn-f6-equip-status` | rest | `{"base_url":"http://127.0.0.1:8001","path":"/equipment/status","method":"GET"}` |
| `cn-f6-order` | rest | `{"base_url":"http://127.0.0.1:8001","path":"/maintenance-orders","method":"POST"}` |
| `cn-f6-notify` | rest | `{"base_url":"http://127.0.0.1:8001","path":"/notify","method":"POST"}` |

### 第 3 步：注册 3 个能力（能力中心 → 能力注册，详见 §15.6）

| 能力 ID | Domain/Name | 类型 | 所需权限 | 执行方式 | 执行参数 |
|:---|:---|:---|:---|:---|:---|
| `cap-f6-equip-status` | equipment / query_equipment_status | query | `equipment.status.read` | `tool.fetch` | `{"connector_id":"cn-f6-equip-status"}` |
| `cap-f6-create-order` | maintenance / create_maintenance_order | command | `maintenance.order.create` | `tool.fetch` | `{"connector_id":"cn-f6-order"}` |
| `cap-f6-notify` | notify / notify_owner | command | `notify.send` | `tool.fetch` | `{"connector_id":"cn-f6-notify"}` |

> 角色（系统设置 → 角色）要有对应 `permissions`——FDE 可让 Admin 在 `r1`（Admin 角色）里勾上这三个权限。


### 第 5 步：运行（两步，中间等人工）

1. ▶ 运行 → 输入 `CNC-01 温度异常，请帮我处理` → 画布走到 **人工确认** 停住（粉色 ⏸，返回 202）
2. 在结果条输 `确认，请继续` → 流程跑完（建单→通知），画布 ✅ 到结束

> 换一个设备状态再跑一遍看另一支：`curl -X POST http://127.0.0.1:8001/_control/equipment -H 'Content-Type: application/json' -d '{"equipment_id":"CNC-01","status":"ok","temperature":42}'`
> → 走 else 分支，LLM 生成「设备正常」答复。

### 第 6 步：发布 + 对话验证

保存后点「**发布**」（发布评审会再校验一次图）→ 前端/API 调 `POST /chat_apps/{app_id}/chat`
（orchestration=flow）即可对话验证。每次会话第一句挂起返回 202，第二句恢复直到完成；
能力调用全量落审计（`earp.capability.call.*`）。

## 7.6 照着搭：客户投诉分流（场景 C）

**前置**：建 KB「客户投诉记录」并传两个样例文档（元数据 `{"vip": true, "customer": "张伟"}` /
`{"vip": false, "customer": "李明"}`，KB 的 metadata_schema 需含这两个字段）；再注册归档能力
`cap-f6-archive-complaint`（complaint / archive_complaint，command，`complaint.archive`，`tool.fetch` →
`cn-f6-complaint` 连接指向 `POST /complaints`）。

**图**（两分支各自「先归档、再话术」——LLM 节点放最后，答复才是页面展示的答案）：

```
开始 → 知识检索(kb_ids=客户投诉记录, 查询={{query}}) → 条件: chunks.0.metadata.vip == true?
   ├─ ✓是 → 能力:归档(VIP) → LLM: VIP 话术（24 小时内专人跟进） → 结束
   └─ ✗否 → 能力:归档(普通) → LLM: 标准话术（3 个工作日内反馈） → 结束
```

**跑**：输入 `张伟反映上次设备安装响应太慢，需要处理` → 命中 VIP 分支（归档 `vip:true`，VIP 话术）；
`李明反映说明书更新不及时` → 普通分支。

> 关键点：条件左值写 `k1.output.chunks.0.metadata.vip`（列表首条元数据，F6 起支持列表下标）；
> 归档节点的 `customer` 参数用 `{{#k1.chunks.0.metadata.customer#}}` 把检索命中的客户带过去。

## 8. 常见问题（FAQ）

| 现象 | 可能原因 / 处理 |
|:---|:---|
| 保存提示"图不合法" | 缺开始/结束、有环、条件分支只连一条边——看提示逐个改 |
| 能力节点 403 | 你的角色没该能力权限（找管理员授权） |
| 工具节点报"连接不存在" | connector_id 填错或连接已删/停用（找管理员） |
| 运行到一半不动 | 遇到人工确认在等人——在结果条输答复提交即可 |
| 等人太久没答复 | 默认 1 小时后自动判"超时终止"；**超时后**用户再说"确认"不会续上，需要重新描述问题 |
| 答案变成一坨 JSON | **最后执行的节点**决定了展示的答案——把 LLM 节点放分支最后，让副作用节点（归档/开单）先执行 |
| 条件总走错分支 | 左值路径写错或漏了列表下标——对照 §4.5 检查字段名；调试时点条件节点看实际输入值 |
| 第二句"它坏了"没指代上 | 上一条消息没有实体（如只回了个"确认"）——把设备名写全 |
| 两轮对话指代不生效 | 换一个**新会话**再试（指代取同一会话的上文）；同一会话里第二句紧跟第一句 |
| QU 节点很慢 | 取消 QU 节点「启用 LLM 升级」勾选 → 纯规则秒回；或让管理员调 QU 升级模板 / 换更快默认 LLM |
| 找不到 Chatflow 入口 | 工作台（一级菜单）→ 左抽屉点 **chatflow**（不是 chat） |
| 画布看不到节点 | 滚轮缩放 / 拖空白平移；卡住就点「清空」再载入「示例」 |
| 想知道能力到底调没调 | 查审计日志：`SELECT event_type, entity_id, detail FROM audit_logs WHERE event_type LIKE 'earp.capability.call%' ORDER BY created_at DESC LIMIT 20;`（tenant 维度） |

## 9. 权限与安全速记

- **能力节点**：每次调用走权限门禁 + 审计（`earp.capability.call.*` 落日志）——审计 SQL：
  `SELECT event_type, entity_id, detail FROM audit_logs WHERE event_type LIKE 'earp.capability.call%' ORDER BY created_at DESC;`
  （detail 里含 execution_id / user_id / role_id / 耗时 / 错误，一次能力调用记 started + completed/failed 两条）
- **工具取数**：数据在外部系统，**不自动按角色过滤**（标注 `domain_filtered: false`）——敏感数据请确认归属
- **人工确认**：等待超时自动终止（默认 1 小时，`EARP_APPROVAL_TTL` 可配），不留僵尸流程
- **失败恢复**：节点失败 → 流程终态 failed（非 500），下游不执行、副作用不重复；挂起超时 → 旧流程终态 timeout，新消息开新流程
