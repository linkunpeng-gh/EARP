# Runtime Spec v1.1 评审反馈分析

逐条评估五项建议与当前 v1.1 Runtime Spec / v5 架构的对应关系。

---

## 总体：三项已覆盖可加强，两项是真正的架构变更

| # | 建议 | 采纳 | 改动 |
|---|------|------|------|
| 1 | Session Runtime Loop | ✅ 采纳，强度不够 | Session 从"一个章节"升级为"Runtime 外层容器" |
| 2 | Decision Engine 位置 | ⚡ 部分采纳 | Policy/Approval 移出，分支决策保留 |
| 3 | Capability Graph | ✅ 采纳，归属 Capability Spec | 写 Capability Center Spec 时核心设计 |
| 4 | Execution 过载 | ✅ 采纳 | Decision Engine / Approval Manager 划出 |
| 5 | Feedback 地位 | ✅ 采纳 | 从第十二章移到核心循环 |

---

## #1 Session Runtime Loop — 已覆盖，强度不够

v1.1 第六章已定义 Session，但第二章核心循环仍是"单次 Request 路径"。Session 作为外层容器被定义了，但没有真正成为 Runtime 的统一抽象。

需重构：第二章核心循环从 `Request → Execution → Result` 升级为：

```
Session（外层容器）
    ├── Loop 1: Request → Execution → Result → Feedback → Evaluation
    ├── Loop 2: Event → Decision → Execution → Result
    └── Loop 3: Evaluation → Knowledge → Planner → Replan
```

---

## #2 Decision Engine 位置 — 架构分歧

你建议 Decision 在 Plan 与 Execution 之间，我在 v5 Runtime Spec 中将其内嵌在 Execution 内部。

分歧原因：Decision 依赖执行时的实时状态（当前库存、审批状态），这些状态在 Planner 规划时不可知。

正确拆分：
- Policy Check（是否允许做）→ 独立于实时状态，Plan Validation 时完成
- Approval Check（是否需审批）→ 独立于实时状态
- 执行分支选择（IF 条件 THEN 分支）→ 依赖实时状态，留在 Execution

---

## #3 Capability Graph — 完全正确，归属 Capability Spec

当前 Capability 是"可检索能力集合"，缺少认知关系：
- `query_alarm`、`query_device_status`、`query_maintenance_log` 之间无关系结构
- Planner 只能靠 LLM 猜测关联

建议 Capability Spec 时设计：

```
Capability Graph
  ├── depends_on
  ├── similar_to
  ├── substitutes
  ├── conflicts_with
  └── domain_relation
```

---

## #4 Execution 过载 — 同意

- Decision Engine → 移到 Decision Layer
- Approval Manager → 与 Policy Engine 合并
- Human Task Manager → Coordination Runtime

Execution 只做三件事：Run Task、Guarantee Consistency、Handle Failure。

---

## #5 Feedback 地位 — 已定义但不够

v1.1 第十二章有完整规范，但位置靠近附录。需内嵌到核心循环，成为 Session 主流程的一部分。
